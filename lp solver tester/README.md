# LP Solver Tester

This directory is an isolated benchmark harness for the exact Tic-Tac-Nope sequence-form LP. It does **not** replace or modify the production solver. The goal is to compare solver/algorithm choices on the same fully enumerated game and reject any speedup that changes the equilibrium.

## Default benchmark cases

The overall command runs four masks with starting player O:

| Case | Hidden cells | Hidden count | Why chosen |
|---|---:|---:|---|
| `two_top_corners` | 1, 3 | 2 | nontrivial reflection symmetry |
| `two_opposite_corners` | 1, 9 | 2 | larger stabilizer subgroup |
| `three_top_row` | 1, 2, 3 | 3 | nontrivial reflection symmetry |
| `three_main_diagonal` | 1, 5, 9 | 3 | larger stabilizer subgroup |

The symmetry is intentional: method 7 can only reduce a mask when that particular mask has a non-identity D4 stabilizer.

## Methods

The runner includes the original production solver and the requested alternatives.

### Baseline — current production solver

Calls `sequence_form_lp.solve_equilibrium(game)` exactly as the repository currently does. Its validated value is the comparison reference for the other methods.

### Method 1 — explicit SciPy HiGHS algorithm

Runs both:

- `scipy.optimize.linprog(method="highs-ds")`
- `scipy.optimize.linprog(method="highs-ipm")`

The LP is otherwise the same O-oriented sequence-form LP as production.

### Method 2 — direct highspy HiPO + threading

Builds the same sparse LP directly as a `highspy.HighsLp` and solves it using HiPO. By default it benchmarks 4 and 8 threads.

HiPO requires `highspy-extras`, installed by `highspy[extras]` in this folder's requirements file.

### Method 3 — HiPO without crossover

Runs the direct highspy HiPO solve with `run_crossover=off`. This tests whether avoiding basis crossover helps when we only need primal/dual equilibrium vectors and then independently certify them.

### Method 4 — exact constraint generation

Uses the complete O realization polytope `Ex=e`, but does not initially include the whole opponent robust-response system. Instead the master problem contains payoff cuts generated by pure X plans.

After each master solve, the native full-game best-response oracle finds X's exact best response. A violated response is added as a new cut. The method stops only when the full-game best response cannot improve beyond tolerance. The dual weights on generated cuts reconstruct X's mixed realization plan.

This is not heuristic pruning: the final candidate is checked against the complete game.

### Method 5 — exact restricted-game / double oracle

Starts from pure best responses to uniform play. It builds restricted sequence catalogs from the union of discovered pure realization plans, solves that much smaller sequence-form game, then computes exact best responses in the full game for both players.

Any profitable full-game response is added. The method stops only when

`best_O_response_value - best_X_response_value <= tolerance`.

The production native catalog already provides the key primitives used here: `best_response(...)`, `uniform_realization()`, and `restricted(...)`.

### Method 7 — exact intra-mask D4 symmetry quotient

Finds the subgroup of the eight board symmetries that leaves the selected hidden mask unchanged. It constructs orbits of information sets and sequences under that stabilizer, restricts both players to invariant realization plans, removes duplicate symmetric flow rows, aggregates the payoff matrix over sequence orbits, and solves the reduced exact LP.

The reduced realization plans are lifted back to every original sequence and validated against unrestricted full-game best responses. If the quotient implementation is wrong, it will fail the same full-game accuracy checks as every other method.

## Accuracy definition

A method is marked `accurate: true` only when all of the following hold on the **full unabstracted game**:

1. O realization flow residual is within tolerance.
2. X realization flow residual is within tolerance.
3. Both realization plans are nonnegative within tolerance.
4. O's unrestricted best response against X and X's unrestricted best response against O close to within tolerance.
5. The candidate payoff lies inside that best-response interval.
6. The method's reported value agrees with the independently computed interval midpoint.
7. When the baseline was run, the value agrees with the original solver within tolerance.

The benchmark uses the production solver tolerance `1e-7` and a comparison/validation tolerance of `5e-7` to allow normal floating-point differences between equivalent LP algorithms.

## Install

From the repository root:

```bash
python -m pip install -r "lp solver tester/requirements.txt"
```

The production native enumerator also needs `g++` or `clang++`, as before.

## Run everything

From the repository root:

```bash
python "lp solver tester/run_benchmarks.py"
```

That command enumerates each board once and then runs:

- original current solver
- method 1: dual simplex
- method 1: IPM
- method 2: HiPO 4 threads
- method 2: HiPO 8 threads
- method 3: HiPO 4 threads, crossover off
- method 4: constraint generation
- method 5: double oracle
- method 7: symmetry quotient

Enumeration time is recorded separately so the reported `solveSeconds` compares LP/algorithm work rather than repeatedly charging tree generation to every method.

## Results

Each run writes both JSON and CSV to:

```text
lp solver tester/results/
```

Files include:

```text
benchmark-YYYYMMDD-HHMMSS.json
benchmark-YYYYMMDD-HHMMSS.csv
latest.json
latest.csv
```

The JSON contains environment/package versions, game dimensions, timing, method-specific metadata, full-game validation residuals, exploitability gap, baseline value error, and the final `accurate` flag.

Results are checkpointed after every completed board case, so an interrupted long run still leaves useful output.

## Useful options

Only benchmark selected methods:

```bash
python "lp solver tester/run_benchmarks.py" --methods baseline,1,5,7
```

Use different HiPO thread counts:

```bash
python "lp solver tester/run_benchmarks.py" --hipo-threads 2,4,8
```

Increase generation iteration caps:

```bash
python "lp solver tester/run_benchmarks.py" \
  --constraint-max-iterations 500 \
  --double-oracle-max-iterations 250
```

Test X as the starting player:

```bash
python "lp solver tester/run_benchmarks.py" --start X
```

Force the Python reference enumerator (not recommended for speed tests):

```bash
python "lp solver tester/run_benchmarks.py" --enumerator python
```

## Interpreting failures

- `status: "ok", accurate: true`: solved and independently certified against the full game.
- `status: "ok", accurate: false`: solver returned a result, but it failed equilibrium/value validation. Treat this method as incorrect for that case.
- `status: "unavailable"`: optional backend (normally HiPO/highspy extras) was not usable on that machine.
- `status: "error"`: implementation or solver raised an exception; traceback is saved in JSON.

A faster method should not be considered for production unless it is accurate on every benchmark case and then passes broader regression testing on additional masks.
